# エージェントと進める概念モデリングの作業指針

作成日：2026年9月13日  
更新日：2026年9月14日  
位置づけ：概念モデリングをエージェントと反復的に進めるための実務ガイド。実装仕様や個別ベンチマークの解説は、必要に応じて別資料で扱う。

## このガイドの目的と章構造

このガイドは、**エージェントとともに概念モデルを作成・利用・改訂し、各定義の目的と根拠、変更による意味への影響を説明するための作業指針**である。対象領域について何を一つと数え、何を区別し、どの関係や考慮事項を記述するかを、利用目的に照らして決める。プロパティは、情報の保存に加え、エージェントの理解・記述・関係の判断を支える役割からも設計する。

この目的を、次の五章で扱う。初回は要件から定義、検証へ進み、その後は見つかった問題に応じて必要な章へ戻る。

1. **第1章：要件と対象範囲を定める。** 誰が何のためにモデルを使い、そのために何を区別する必要があるかを明らかにする。
2. **第2章：モデルを定義する。** 必要な概念・関係・プロパティを、意味と導入理由が説明できる形で記述する。
3. **第3章：実例でモデルを検証する。** 問い、典型例、境界例、情報不足や矛盾する事例を使い、モデルの過不足を確認する。
4. **第4章：意味への影響を確認してモデルを改訂する。** 不足や例外を差分として分析し、局所追加、共通化、再構成などの対応を選ぶ。
5. **第5章：運用から学び、次の反復へつなげる。** 即興的な編集や逸脱を振り返り、要件・定義・作業方針のどこを改善するべきか判断する。

今回の関心と各章の対応は、次のとおりである。検証を独立した第3章に置き、定義・改訂・運用のそれぞれで利用する。

| 検討の柱 | 主に扱う章 |
| --- | --- |
| 要件のヒアリングと記述 | 第1章 |
| モデル定義の記述と分析 | 第2章、第3章 |
| 既存モデルとの差分分析と対応方針の選定 | 第4章 |
| 運用時の複雑な事情に対応する総合的な指針 | 第5章を中心に全章 |

作業環境は、エージェントの現在のコンテキスト、簡単なファイルシステムとCLI、gitによるテキストの差分・版管理を想定する。データベース、外部接続、コンテキストを超えた記憶、スクリプトによる形式的検証は前提としない。ここでいう検証は、定義・記録・事例を読み合わせ、問いに答える根拠と改訂の影響を確認する作業を指す。小さな補足は採用理由と影響の確認で扱い、全工程を毎回実行する必要はない。

## 本ガイドを通じて用いる基本的な区別

要件整理から運用まで、モデルの層、記述の来歴、情報状態を区別する。各区分は、記述の意味と根拠を確認するために用いる。

### モデルの層：定義とインスタンス

最初の区別は、**何を一つの対象として扱うかを定める記述**と、**その定義に照らして認識した個別対象の記述**である。この二つは、モデルの設計とデータの記述を分けるための基本語彙になる。

| 区分 | 役割 | 例 |
| --- | --- | --- |
| モデル定義 | 対象の意味、単位、属性、関係を定める | 「評価」は、主体が対象を特定の基準・時点で判断したもの |
| インスタンス | 定義に照らして認識した個別対象を記述する | 機関Aが事業Bについて行った2025年の評価 |

モデル定義を変更すると、既存インスタンスの読み方や分類が変わることがある。第2章では定義を作り、第3章ではインスタンスを使って定義を検証し、第4章では定義変更が既存インスタンスへ与える影響を確認する。

### 記述の来歴：主張、情報源、根拠、モデリング上の判断

次の区別は、**対象について何が述べられているか**と、**その記述をどこから得たか**、**どの箇所を根拠として採用したか**、**モデル側でどの設計判断を行ったか**を分けるために用いる。

| 区分 | 役割 | 例 |
| --- | --- | --- |
| 主張 | 人物・組織・資料が対象について述べた内容 | 報告書Rは「事業Bは有効だった」と述べる |
| 情報源 | 主張や値の出所となる資料・人物・記録 | 報告書R、作成者、発行日 |
| 根拠 | 値や解釈を採用する際に参照した具体的な箇所や内容 | 報告書R第3節の「開始後3か月を評価した」という記述を対象期間の根拠とする |
| モデリング上の判断 | 概念、関係、プロパティを導入・整理した理由 | 評価の食い違いを比較するため「評価基準」を設ける |

この区別によって、資料の内容とモデル作成者の解釈を追跡しやすくなる。とくに、**値を支える根拠**と**その値を格納するプロパティを設けた理由**は別の判断として記録する。「報告書が有効と述べた」という主張の確認と、事業が実際に有効だったかの判断も分ける。

### 情報状態：未確認、不明、該当外、否定、競合

記述する値について、確認の進み具合、項目の適用可能性、主張間の一致を必要に応じて区別する。

| 区分 | 意味 | 例 |
| --- | --- | --- |
| 未確認 | 必要な資料や箇所をまだ確認していない | 評価基準の記載を未調査 |
| 不明 | 確認した範囲では確定できない | 本文と付録を読んでも評価基準を特定できない |
| 該当外 | 定義上、その項目が対象に適用されない | 単独制作における共同制作者の役割 |
| 否定 | 定めた範囲について、存在や成立を否定する内容が確認された | 資料が「外部評価は実施していない」と明記している |
| 競合 | 同じ対象・時点・基準について、両立しない主張がある | 同じ資料の発行日について記録が食い違う |

これらは必要な区別を示す語彙であり、一つの排他的な分類へ固定しない。例えば、主張が競合するため値が不明になる場合がある。否定には確認範囲と情報源を添える。異なる評価主体や基準による判断の違いは、比較すべき差異として保持し、内容が異なるだけで競合と扱わない。

この区別は、第1章の要件整理では必要な不確実性表現を決めるために使い、第2章ではプロパティ設計へ反映し、第3章以降では情報不足とモデル不足を切り分けるために使う。

## 第1章　要件と対象範囲を定める

この章の目的は、**誰が、何を判断・説明するためにモデルを使い、そのために何を区別する必要があるか**を明らかにすることである。ヒアリングでは、一般的な利用要件から始め、概念上の区別、情報の扱い、変更時の条件へ段階的に進む。

### 1.1 ヒアリングを三つの層に分ける

ヒアリングでは、利用目的を確認し、その目的に必要な概念上の区別と運用条件を具体化する。論点を次の三層に分ける。

**第1層は、利用目的と成果の層である。** 誰が、どの場面で、何を判断・説明したいのか、どのような回答や成果物が役立つのかを確認する。ここでは「複数機関の評価を比較したい」「事業ごとの論点を説明したい」といった利用目的を得る。

**第2層は、概念上の区別の層である。** 利用目的を満たすために、何を一件として数え、どこまでを同じ対象とみなし、どの用語や関係を区別するかを確認する。対象範囲、対象単位、同一性と時間、用語、関係が主な論点になる。

**第3層は、情報と運用の層である。** どの情報源を用い、未確認・不明・競合をどう扱い、どの意味を維持しながら変更するかを確認する。根拠の粒度、不確実性、変更条件、保守のしかたが主な論点になる。

第1層は一般的な要件ヒアリングと共通する。第2層は、対象の単位・同一性・概念間の関係を定義するという、概念モデリングに固有性の高い検討である。第3層はデータ管理や研究実務とも共通するが、情報の来歴や変更条件をモデルの意味へ結び付ける点を重視する。回答に応じて三層を往復し、必要な区別をプロパティ設計へ反映する。

### 1.2 利用場面から対象範囲と意味上の境界を定める

ヒアリングは、具体的な利用場面を一つ置くところから始める。典型的な事例に加え、「現在の整理では判断を誤りそうな例」を一つ得ると、必要な区別が見えやすい。

例えば「複数機関の評価を比較したい」という要件では、まず比較の目的と期待する回答を確認する。そのうえで、報告書を一件とするのか、個別の評価を一件とするのか、評価主体・基準・対象期間の違いをどの単位へ反映するのかを検討する。

第2層では、次の論点から利用目的に関わるものを選ぶ。

- **対象範囲：** どの対象をモデルへ含め、境界例をどのように扱うか。
- **対象の単位：** 事業、報告書、主張、評価などのうち、何を一件として扱うか。
- **同一性と時間：** 改名、改訂、担当変更、再評価の前後をどの単位で同一とみなすか。
- **用語：** 同義語、近接概念、資料ごとの用法差をどのように整理するか。
- **関係：** 種類、部分、所属、原因、評価対象など、判断に必要な関係をどの粒度で表現するか。

第3層では、情報の来歴と運用条件を具体化する。

- **根拠と情報源：** どの値や解釈について、どこまで出所を追跡するか。
- **不確実性：** 未確認、不明、該当外、否定、競合のうち、どの状態を区別するか。
- **変更条件：** 何の意味を維持し、どの変化を要件や定義の再検討につなげるか。
- **参照の意図：** 特定の対象を追跡するのか、利用時に条件を満たす対象を選ぶのか。候補が複数ある場合や特定できない場合をどう扱うか。

初回のヒアリングでは、すべての論点を網羅するよりも、利用目的に影響する区別を優先する。確定した要件、作業仮説、未決事項を分けて記述すると、第2章で定義を設計しやすい。

### 1.3 問いをモデルの要件として記述する

「何を知りたいか」は、後でモデルを検証できる程度まで具体化する。能力質問（コンピテンシー・クエスチョン：CQ）はそのための一つの方法である。本ガイドでは、モデルに必要な表現能力を点検する自然言語の問いとして用いる。要件は「資料の主張と分析者の解釈を区別する」のような声明文でも記述できる。

例えば「評価を比較したい」という要件は、次のような問いへ具体化できる。

- 同じ事業について、どの機関が、いつ、どの評価基準で、どのような判断をしたか。
- 評価が異なるとき、対象期間や評価基準の違いを確認できるか。
- 説明情報が不足し、違いの理由を保留すべき評価を識別できるか。

CQは、第1層の利用目的を、第2層の概念上の区別と第3層の情報要件へ橋渡しする。問いごとに、期待する回答の形、必要な区別、回答を保留する条件を添えると、第3章での検証にも使いやすい。

### 1.4 第1章のまとめ

第1章の成果は、**利用目的、対象範囲、必要な区別、情報と根拠の扱い、未決事項**である。これらを問いや声明文で記述し、第2章の設計と第3章の検証に用いる。

## 第2章　モデルを定義する

この章の目的は、第1章で定めた要件を、**意味と導入理由が説明できる概念・関係・プロパティ**へ変換することである。資料に現れる語を手掛かりとしながら、要件に必要な区別を表現する構造を設計する。あわせて、エージェントが直接モデルを記述する場合には、推論と記述を支える補助的なプロパティ設計も検討する。

### 2.1 定義には意味、単位、導入理由を書く

中心となる概念には、少なくとも意味、対象単位、典型例と境界例、主な関係、重要なプロパティの役割を書く。時間、適用条件、不確実性、外部定義との対応、編集方針は、必要な箇所へ追加する。

説明の詳しさは、概念が判断へ与える影響に合わせる。中心概念には定義と適用例を詳しく記述し、補助概念は簡潔にまとめる。

定義を作る際には、次の区別を優先的に点検する。

- 種類、個体、部分をそれぞれ適切な階層や関係として表現する。
- 対象そのものの属性と、主体による評価を分けて表現する。
- 事実、推論、推奨には、それぞれの役割が読める構造を与える。
- 同名のプロパティには、対象をまたいで一貫した意味を与える。
- 同じ概念の別名は対応づけ、意味上の重複を整理する。

例えば「事業Bの評価＝良い」とだけ記述すると、評価主体や評価基準の違いが失われる。複数の評価を比較することが目的なら、「評価」を独立した対象として表す意義がある。一方、単一の確定判断だけを保存する用途では、より簡潔な構造が適する。構造の細かさは利用目的に合わせる。

### 2.2 プロパティの役割を区別する

プロパティには、少なくとも三つの役割がある。第一は、評価主体や参照資料のように**記録しなければ失われる情報**である。第二は、開始日と終了日から求める期間のように**他の情報から導出できる情報**である。第三は、利益相反、長期的影響、評価の限界のように、現時点で値がなくても**確認すべき観点を残すための項目**である。

三つ目の項目は、現在の値の有無よりも、問いや判断への寄与で採否を決める。「この観点があることで何を問い、どの判断が変わるのか」を説明できることを導入条件とする。

導出可能な情報を保存するかどうかは、再現性と意味によって決める。計算で安定して再現できる値は導出規則として持つ方法がある。一方、当時の判断や過去時点の分類は、現在の導出値と一致していても記録する意義がある。

### 2.3 非構造化資料を解釈して構造へ変換する

レポートに現れる語は、情報源の主体、目的、対象範囲、時点とあわせて解釈する。必要箇所を位置が分かる形で抜き出し、定義、観察、評価、因果解釈、提案を区別する。そのうえで、既存概念で表現するか、新しい意味として導入するかを検討する。

外部機関が用いる分類は、その機関の目的に合わせて解釈する。別の目的へ適用する際は、目的との対応を確認する。複数資料の定義が異なる場合は、共通部分と相違点を保持すると比較しやすい。

明示的な定義、複数資料からの解釈、こちらのモデリング判断は区別して記述する。資料から採用する値や主張は、該当箇所が支える範囲に合わせる。

### 2.4 エージェントの理解・記述・関係の判断を支える

プロパティを設計する際には、**何を記録するかに加え、その記述がエージェントの作業をどう支えるか**を検討する。ここでは、対象全体を自然言語で説明する方法と、関係する対象の条件を記録して利用時に照合する方法を扱う。両者は採用候補となる経験則であり、対象と作業に応じて効果を確認する。

#### `_description` に対象全体の説明を記述する

`_description` は、個別のオブジェクトについて、主体、出来事、背景、他の対象との区別、未確定事項をまとまりのある文章で記述するプロパティである。必要に応じて長文を許容し、長さは対象の複雑さに合わせる。通常プロパティへ分解する前の文脈を保持し、各項目の記述や後日の再編集に利用する。

**モデル定義には説明欄の記載方針を書き、インスタンスには個別対象の説明を書く。** 定義に付ける用語解説と、エージェントが事例ごとに生成する説明文は、記述の層が異なる。例えば、記載方針は次のように定められる。

> `_description` には、この対象の主体・出来事・背景・他の対象との区別・未確定事項を、資料に基づいて記述する。資料の内容と作成者の解釈を区別し、通常プロパティを判断する際の文脈を示す。

生成時には、説明を書いてから通常プロパティを記述する。通常プロパティが先に作られている場合は、説明を加えた後に値を再点検する。JSONやYAMLでキーを並べる順序とは別に、この作業順を定義する。保存後には、説明を対象理解の手掛かりとして利用する。説明と値が食い違った場合は、原資料とモデル定義へ戻り、両方を見直す。

「隠し」は通常の表示から省くという意味で用いる。編集・点検時には説明を参照できるようにする。接頭辞 `_` 自体に特別な効果は想定しない。説明の生成と保存を分け、初回の生成だけに役立つ記述は一時メモに置き、再読や改訂にも役立つ内容を保存する方法も選べる。

この設計には、分類結果の前に中間記述のフィールドを生成させる近接研究がある。ただし、長い対象説明が複雑な概念モデルの品質を改善する効果は、本ガイドの利用場面で検証する仮説として扱う。関連する実験と実装例の範囲は付録B・資料6、7に示す。

#### 関係する対象の条件を記録し、利用時に照合する

参照方式は、**特定の対象の同一性を維持したいか、条件を満たす対象を選びたいか**に基づいて選ぶ。安定したIDなら、対象の改名だけで参照を書き換える必要はない。一方、分割・統合や定義変更の後には、IDで参照先が見つかっても、関係の意味が適切かを再確認する必要がある。

| 参照の目的 | 例 | 記録するもの |
| --- | --- | --- |
| 特定の対象を追跡する | 前回の分析で根拠にした評価報告書 | 安定したID、書誌情報、記録の位置など、対象を特定する手掛かり |
| 利用時に条件を満たす対象を選ぶ | 同じ事業を別の主体が評価した事例 | 参照条件と照合範囲。対象の追加や更新に応じて候補を選び直す |
| まだ特定できていない対象を探す | ある判断変更の契機となったやり取り | 対象の特徴、関係の根拠、未確定事項。候補を照合して特定する |

条件に基づく参照では、プロパティに参照先が満たすべき特徴を自然言語で記録し、説明・比較などに使う時点で、エージェントが対象の記述と照合する。ここではこの作業を「参照先の解決」と呼ぶ。例えば、ある評価の比較候補を探す条件は、次のように書ける。

> 現在読み込んでいる評価記録のうち、この評価と同じ事業・対象期間を扱い、異なる主体が行った評価。評価基準の違いは比較内容として示す。

この条件は、実際に比較可能かを検討するための候補を指定する。特定の評価との固定的な関係を、条件に基づく参照へ置き換える場合は、**関係の意味が変わるか**を確認する。IDと条件を併用する場合にも、条件を満たさなくなったときに同じ対象を追跡するのか、別の対象を選び直すのかを定める。

参照先の解決では、次の事項を必要な粒度で明記する。必ずしも別々のプロパティに分ける必要はなく、短い文章でもよい。

- **照合範囲と時点：** どの記録・版から候補を選ぶか。
- **関係の意味と根拠：** 単なる比較候補なのか、出典・帰属・因果などを主張する関係なのか。どの記述がその関係を支持するか。
- **結果の扱い：** 一件を特定した、複数が該当した、候補を絞れない、該当記録がない、情報が足りない、を区別する。
- **解決の時点：** 原則として利用時に照合する。後続の記述がその関係に依存する場合は、その記述より前に照合する。

複数の対象を選ぶ条件なら、複数件の該当は正常な結果である。一件を特定したいのに候補が残る場合には、未確定として示す。「該当記録がない」は、照合範囲における結果として述べる。因果関係や発言の帰属は、特徴の一致に加えて、その関係を支持する記録を必要とする。

過去の説明を再現する必要がある場合には、条件とともに、選んだ対象、判断の根拠、参照した版を残す。現在の条件で選び直した結果とは区別する。この方法は、記載時の特定や参照更新の負担を利用時の照合へ移すため、総負担は第3章で確認する。特徴による参照と自然言語による照合の先例は、付録B・資料8、9を参照する。

### 2.5 最小限だが説明可能な構造を作る

モデルの初版は、現在の目的と問いに必要な構造から始める。最小化では項目数よりも、必要な区別を明示的かつ簡潔に表現できることを重視する。自由記述へ移す場合も、その区別を再構成できる情報を保つ。

構造を追加するときは、「どの問いまたは事例のために必要か」「既存構造では何が歪むか」を短く説明できるようにする。この説明が、第3章で過剰な構造を検出するときの基準になる。

プロパティの役割は、対象領域の情報と作業支援の両面から確認する。`_description` は理解を補助し、参照条件は関係の意味や対象の選び方も保持する。そのため、参照条件を一律に補助情報と扱わない。重要な区別については、独立した項目にするか自然言語で保持するかを選び、どの記述から判断できるかを明示する。

### 2.6 第2章のまとめ

第2章の成果は、**概念の意味と対象単位、各プロパティの役割と採用理由、記載手順と参照方式**である。定義を作業仮説として第3章の事例へ適用し、必要な区別を表せるか、記述と利用の負担が許容できるかを確認する。

## 第3章　実例でモデルを検証する

この章の目的は、第2章で作ったモデルが、**第1章で定めた問いと現実の事例を適切に扱えるか**を確認することである。必要な区別を表せるか、構造が簡潔か、情報不足や競合を区別して記録できるかを確認する。

### 3.1 多様な事例で検証する

評価には、典型例、境界例、対象外の例、情報不足の例、情報源が衝突する例、モデル作成時とは別の例を含める。この組み合わせによって、想定内の記述能力と想定外への頑健性を確認する。

各事例では、モデルが必要な区別を表現できるか、同じ定義から一貫して解釈できるか、情報源の記述とこちらの判断を区別できるかを確認する。また、自由記述や例外処理へ負担が集中している箇所も見る。

### 3.2 問いへの回答状況を切り分ける

第1章で作ったCQや具体的な問いを使い、回答と、その根拠となる定義・記録箇所を示す。回答状況を次のように分ける。

- 定義と記録済み情報から答えられる場合は、今回の範囲では表現と情報が足りている。
- 表現はできるが値が未取得の場合は、主に情報収集・記録の問題である。
- 必要な概念や関係がモデルに未定義の場合は、モデル拡張の候補とする。
- エージェントの一般知識や推測を要する場合は、モデル外の補助推論として明示する。
- 合意した対象範囲の外にある場合は、要件変更として扱う価値を検討する。

記録された定義と条件から関係を解決する推論も、モデルを使った回答に含める。その際は、どの記述が条件を満たしたかを示す。モデル外の知識で不足を補った場合は、その前提を別に示す。これによって、動的な推論を利用しながら、モデルが支えた判断の範囲を確認できる。CQに加え、用語の一貫性、情報源への忠実さ、変更時の追跡可能性も確認する。

### 3.3 過剰なオブジェクトやプロパティを見つける

構造の整理候補には、似た項目の反復、値の変動の少なさ、空欄の多さ、継続的な細分化、他項目からの安定した導出、問いとの対応の薄さといった兆候がある。

これらは構造を点検するきっかけとして使う。候補を外したモデルで同じ事例とCQを扱い、失われる区別、判断の変化、自由記述へ移る説明負担を比較する。複数項目が重複しているように見える場合は、個別の削除と項目群の整理を双方で確認する。

空欄が多い項目でも、未確認の重要な観点を保持する役割を持つ場合がある。各項目は、値の充足率よりも要件や判断への寄与で評価する。

### 3.4 説明欄と参照方式の効果を比較する

作業支援のための設計は、記載・改訂・利用を通じた品質と負担で評価する。同じ資料、問い、モデル定義を使い、比較する要素を絞る。日常の小さな編集には影響確認を用い、継続的に使う記述方針を選ぶ際に、次のような比較を行う。

| 検討対象 | 比較する案 | 確認する結果 |
| --- | --- | --- |
| 説明欄 | 説明なし／短い対象要約／背景・区別・未確定事項を含む説明 | 通常プロパティの正確さ、重要な区別の保持、資料にない補完、修正量 |
| 説明の保存 | 生成時の一時メモ／インスタンスに保存 | 再読・改訂への寄与、読み直す量、説明と値を更新する負担 |
| 参照方式 | 固定参照／自然言語の条件／併用 | 参照目的への適合、解決の根拠、未確定結果の扱い、記載と更新の負担 |

説明欄の比較では、説明を書く時点と通常プロパティを見直す手順をそろえ、使用したモデルと指示も記録する。文章が流暢になったことと、内容が正確になったことを分けて評価する。一例での改善は、その事例での効果として扱い、継続採用の前に性質の異なる事例でも確認する。

参照方式の比較では、対象の改名、分割・統合、類似対象の追加、該当対象の削除、判断材料の欠落を試す。固定参照では同じ対象を追跡できるか、条件参照では更新後に条件を満たす対象を選べるかを確認する。同じ条件でも記録の版が変われば、適切な結果が変わる場合がある。同じ入力で判断が変動する問題とは分けて扱う。

### 3.5 複数の評価軸を保つ

モデルの評価では、必要な区別を表現できること、定義が明確であること、情報源へ忠実であること、記述負担が許容できること、改訂の影響を追跡できることを分けて見る。総合評価を作る場合も、各軸の変化を併記する。

検証では、十分に機能する部分、未確定の部分、次の改訂対象を明らかにする。

### 3.6 第3章のまとめ

第3章の成果は、**維持できる部分、情報収集で補える部分、モデル変更が必要な部分、対象範囲を見直すべき部分**の切り分けである。モデル変更が必要な事項は、第4章で意味への影響を分析して対応方針を選ぶ。

## 第4章　意味への影響を確認してモデルを改訂する

この章の目的は、第3章で見つかった不足や例外を、**既存の意味との関係を確認しながらモデルへ取り込むこと**である。変更量の大小よりも、どの意味と既存事例へ影響するかを基準に改訂方法を選ぶ。

### 4.1 テキストの差分と意味の差分を分ける

プロパティを一つ追加するだけでも、新しい観点の追加、既存概念の明確化、適用範囲の拡大、対象の同一性の変更では意味上の影響が異なる。変更前に、少なくとも次を確認する。

- 何を表現できず、どの事例やCQで問題になったか。
- 既存項目を使うと、どの意味が歪むか。
- 一件だけの事情か、条件付きで共通する事情か、定義全体の不足か。
- 既存の比較や事例分類に影響するか。
- 名称・定義の明確化、統合、分割、関係への置換、新設のうち、最も適した変更はどれか。

そのうえで、個別事例だけに残す、条件付き項目にする、共通定義へ追加する、既存項目の定義を修正する、対象や関係を再構成する、変更自体を撤回する、といった対応を選ぶ。

共通化は、出現回数だけでなく意味上の重要性と独立性で判断する。一度の反例でも中心的な区別を変える場合は重く扱う。多数の出現については、独立した事例から生じているかを確認する。

### 4.2 局所追加と共通定義の改訂を分ける

ある事例で「評価対象期間」が必要になり、既存定義への影響を限定できる場合は、局所的に追加して有用性を確かめられる。その後、他の事例でも同じ区別が必要か、記録可能か、既存例へ適用すると何が変わるかを検討して共通化を判断する。対象の数え方や関係の意味を変える場合は、最初から定義改訂または再設計の案として扱う。

局所的で可逆的な追加は、既存項目では意味を十分に表せず、追加の有用性と意味を説明できる場合に採用しやすい。既存定義への影響は明示し、小さな変更は短い注記とgitの差分で記録する。

### 4.3 保護する意味を決める

柔軟な編集では、「変更可能な部分」と「維持する意味」の双方を明示する。例えば「評価」という概念では、主体、対象、時点、基準の区別を保護しつつ、根拠箇所や補足事情は局所的に追加できる、といった方針を持てる。

次のような変更は、定義改訂として扱い、元の版と影響範囲を確認する。

- 一件と数える単位や同一性の基準を変える。
- 比較中の評価軸や分類境界を変える。
- 中心概念の意味を再解釈し、他の記録の意味まで変える。
- 外部標準との意味の一致を要件としている箇所を独自定義へ変更する。

こうした変更では、元の版を残し、新しい版として改訂し、影響する事例を確認する。再現対象となる確定済み分析は、その分析時の版を参照できるようにする。

情報源の主張を確定事実として扱うには、その判断を支える根拠が必要である。出典を外して事実へ置き換える編集は、版を分けるだけでは正当化できない。同様に、特定の事例を望む分類へ入れるために定義を変える場合は、改訂理由が他の事例にも通用するかを検討する。それまでは、現行定義での判定と、定義の再検討案を分けて保持する。

### 4.4 作業の局面を区別する

作業時には、「探索する」「既存定義で記述する」「既存定義を拡張する」「再設計する」「評価条件を固定する」という局面を意識する。これは、既存の意味を維持する作業と、その意味自体を再検討する作業を明確に分けるための区別である。

例えば、既存モデルへ不足を追加する作業では既存の意味を基準に置き、対象単位を再設計する作業では基準自体を検討対象にする。比較中に新しい重要な要件が見つかった場合は、その要件を記録し、比較条件の次版へ反映する。

### 4.5 説明と参照条件への影響を確認する

通常プロパティを更新したときは、関連する `_description` に古い内容がないか確認する。説明を変更したときも、対象単位、分類、関係の解釈が変わるかを点検する。表示から省かれる項目でも、後続の判断に使う内容は改訂の対象となる。

参照先の分割・統合では、固定参照の対応先と、条件参照の該当範囲を確認する。参照条件そのものの変更は、選ばれる対象の範囲を変える改訂として扱う。影響のある範囲で再照合し、以前の解決結果を現在の結果として使えるかを確認する。過去の分析結果は当時の条件と版に対応付けて保持する。

### 4.6 第4章のまとめ

第4章の成果は、**変更内容と理由、維持した意味と変更した意味、既存事例への影響**を説明した改訂である。説明欄や参照条件への影響も確認し、改訂結果と判断記録を第5章の振り返りに用いる。

## 第5章　運用から学び、次の反復へつなげる

この章の目的は、実際の利用中に生じた即興的な編集、例外、誤解、要件変更を、**次のモデル改善と作業方針の改善へ還元すること**である。局所的にうまくいった編集と、共通ルールとして採用すべき変更は分けて評価する。

### 5.1 即興的な編集を二つの観点で評価する

運用中の編集は、まずその事例で有用だったかを確認し、その後で共通化する価値があるかを判断する。

例えば、ある事例への補足項目によって誤読が減ったなら、その編集には局所的な価値がある。共通化は、他の事例でも同じ区別が有用かを確認して判断する。また、後で撤回した変更でも、当時の情報に基づく暫定判断として合理的だった可能性を評価する。

振り返りでは、少なくとも次を確認する。

- 当時の情報と方針から見て、その判断は合理的だったか。
- その事例で失われていた情報や区別を回復できたか。
- 新しい項目の意味と根拠を説明できるか。
- 変更範囲は必要な箇所に限定されていたか。
- 他の事例との比較可能性を損なわなかったか。
- 入力・読解・保守の負担に見合ったか。
- 同種の問題を次回早く認識できる知識を残したか。

### 5.2 逸脱を「何が表現できなかったか」でまとめる

逸脱は、「何を表現する必要が生じたか」という意味上の問題でまとめる。異なるキーが同じ不足を補う場合も、同じキー名が別の問題を扱う場合も、この整理によって区別できる。

振り返りの結果は、少なくとも次のどこへ戻すべきかを判断する。

- **要件の問題：** 利用目的や必要な区別自体が変わった。
- **定義の問題：** 概念や関係の意味が曖昧または不足していた。
- **情報収集の問題：** モデルは表現できるが、必要な値や根拠が得られていなかった。
- **運用の問題：** 定義は十分だが、入力や編集の手順が誤解を誘った。

問題の種類に応じて戻り先を選ぶ。要件の変化は第1章、定義不足は第2章、検証条件の不足は第3章、変更規則の問題は第4章へ戻す。

### 5.3 一回の作業を小さな反復として回す

日常の作業は、次の六段階を一つの小さな反復として扱う。

1. 対象となる実例と、今回答えたい問いを確認する。
2. 関係する定義と、保護する意味を読む。
3. 既存定義で記述し、無理が生じる箇所を見つける。
4. 必要なら局所追加や変更案を作り、代替案と比較する。
5. 影響する既存例と境界例で、維持する意味と変更する意味を確認し、必要な説明と参照結果を更新する。
6. 採用した変更と理由を残し、共通化や再設計が必要なものだけ次の検討へ回す。

この反復では、要件、モデル、実例を段階的に育てる。初回は重要な要件から確定し、逸脱は局所対応と共通化を分けて扱う。

### 5.4 記録量は変更の影響に比例させる

重要な変更では、事例、問題、採った対応、理由、影響、未決事項を残す。小さな補足は一文で記録する。記録量は、後から判断を再構成できる範囲で変更の影響に比例させる。

例えば、次の程度の記録から始められる。

> 事例E17では短期の成果を評価していた。「発行日」は資料の時点を表し、評価対象期間とは役割が異なるため、「評価対象期間」を局所追加した。他の評価との比較にも必要か確認し、共通化を判断する。

この短い記録から、問題となった事情、既存項目との役割差、行った変更、未決の判断を追跡できる。

### 5.5 定義・インスタンス・利用時の結果を分けた記述例

次は、架空の評価資料を使った記述例である。モデル定義には各プロパティの意味と記載方針を置き、インスタンスには個別の値を置く。参照条件を照合した結果は、利用時の結果として分けて示す。YAMLはこの区別を読みやすくするための例示形式であり、同じ内容をMarkdownの見出しと文章で記述してもよい。

```yaml
目的: 複数機関による事業評価の相違を比較する
対象範囲: 現在の作業で読み込んだ資料に記述された評価
問い:
  - 同じ事業・対象期間について、主体と基準による判断の違いを説明できるか
モデル定義:
  評価:
    意味: 主体が対象を特定の基準と時点で判断したもの
    単位: 暫定的に資料中の個別判断ごとに一件と数える。同一判断の再掲が疑われる記録は未決として扱う
    プロパティ:
      _description: 個別評価の背景と比較上の留意点。通常の一覧では省略する
      主体: 判断を行った人物または組織
      対象: 判断の対象となった事業
      基準: 判断に用いた観点
      評価時点: 判断が行われた時点
      対象期間: 評価が対象とした期間
      判断: 資料が当該主体に帰属させている判断内容
      根拠: 各値を支持する資料の箇所と記述
      比較候補の条件: 利用時に比較候補を選ぶ条件。固定的な参照を意図しない
    記載手順: 資料に基づく説明を書き、通常プロパティを記述して両者を点検する
    編集方針:
      維持する区別: 主体・対象・基準・評価時点・対象期間
      局所追加: 比較に必要な補足事情は理由を付して暫定追加できる
      定義改訂: 一件と数える単位や、関係の意味を変更する場合
インスタンス:
  評価1:
    _description: >
      機関Aは事業Bの2025年4月から6月について、参加人数を基準に目標達成と判断した。
      参加者の理解や長期的な効果については、それぞれの評価基準と資料を確認する。
    主体: 機関A
    対象: 事業B
    基準: 参加人数
    評価時点: 2025年7月
    対象期間: 2025年4月から6月
    判断: 目標を達成した
    根拠: 報告書R第3節に、機関Aが7月に4〜6月の参加人数を評価し、目標達成と判断した旨の記載
    比較候補の条件: 現在の記録にある評価のうち、同じ事業・対象期間を別の主体が評価したもの
  評価2:
    _description: >
      機関Cは事業Bの同じ対象期間について、参加者の理解度が目標に届かないと判断した。
      参加人数を扱う評価と比較する際は、判断の違いと基準の違いをあわせて説明する。
    主体: 機関C
    対象: 事業B
    基準: 参加者の理解度
    評価時点: 2025年7月
    対象期間: 2025年4月から6月
    判断: 目標に届かなかった
    根拠: 報告書S第2節に、機関Cが7月に4〜6月の理解度を評価し、目標未達と判断した旨の記載
    比較候補の条件: 現在の記録にある評価のうち、同じ事業・対象期間を別の主体が評価したもの
利用時の結果:
  照合範囲: この例の評価1と評価2
  評価1の比較候補: 評価2
  選定根拠: 事業と対象期間が一致し、評価主体が異なる
  説明: 参加人数と理解度という基準の違いを伴うため、両者の判断を分けて提示する
未決事項:
  - 同じ判断が別の報告書に再掲された場合の扱い
```

この例の比較候補は、照合範囲を明示して選んだ結果である。記録を追加した場合は条件を再照合する。説明を過去の分析として保存する場合には、参照した版も記録する。日常の記録では、この例の全項目を一律に必須とせず、必要な区別と根拠に合わせて項目数を調整する。

## 付録A　先行する手法から何を借りるか

この付録は、五章の作業を支える参考資料を位置づける。既存のオントロジー工学やLLM支援手法について、それぞれが得意とする局面から本ガイドに有用な考え方を取り入れる。

以下の表は、各手法について、どの章で何を参考にするかを示す。

| 手法 | 主に参考にする点 | 関係する章 | 適用時の調整 |
| --- | --- | --- | --- |
| OntoChat | 利用場面から要件やCQを具体化し、問いを整理する対話 | 第1章、第3章 | LLMの回答可能性とは別に、モデル内の定義と記録情報で充足を確認する |
| OntoExtend | 既存定義を再利用し、不足を限定的な差分として扱うこと | 第4章 | 再設計局面では、既存定義そのものも検討対象に含める |
| Linked Open Terms（LOT） | 要件、概念化、評価、保守を反復的につなぐ全体像 | 全章 | 本ガイドの作業環境に必要な工程を選択して適用する |
| Bench4KE | CQ生成手法を共通の入力・参照質問・評価条件で比較すること | 第3章、第5章 | モデル形成・改訂規則全体の評価は、本ガイド独自の応用として設計する |
| Neo4j Ontology Builder Assistant | 要件と根拠に対応した最小限の定義を重視すること | 第2章 | 探索段階では、将来の判断に寄与する観点も候補として保持する |

これらの手法は、要件の具体化、モデルの作成・拡張、工程管理、質問生成の評価という異なる役割を担う。Bench4KEの参照版が直接評価する対象はCQ生成であり、モデル定義や改訂規則全体の品質とは分けて扱う。

第2章の説明欄と条件参照には、別の研究群を参照する。中間記述を伴う構造化出力の研究は説明欄の近接例、INSは特徴による参照と遅延解決の先例、LOTUSは自然言語の条件による結合の例である。LOTとLOTUSは別の手法である。それぞれの実装を導入せず、今回の作業へ移せる考え方を利用する。

二つの設計の負担を整理する際には、表記の認知的次元も参考になる。同枠組みが扱う、早すぎる決定の要求、変更のしにくさ、補助的な記述といった観点を使い、記載時・改訂時・利用時の負担を比較できる。これは人間による表記利用の分析からの類推であり、エージェントへの効果は別途確認する（付録B・資料10）。
