# 組織・製品・業務の参照モデル

## 目的と対象

組織方針、製品の方向性、働き方、業務手順を、利用者・働く人・組織への影響から判断するために使います。比較する対象は、方針や運用案と、その適用範囲です。技術構成そのものが主要な論点なら [ソフトウェア工学](software-engineering.md)、研究計画への配分なら [学術研究](academic.md) の区別を補います。

個人の作業、部門の運用、組織全体の方針を区別し、誰が実施し、誰が利益・費用・リスクを引き受けるかを示します。同じ製品の利用でも、試行する部門と全社では依存関係や支援の条件が異なります。

## 得られる価値と負担の移転

価値は、利用者の目的達成、生産性、信頼性、安全、定着、収益、費用、働く人の状態、組織の方針との整合など、今回の目的に照らして判断します。これらは同じ成果ではありません。売上や処理件数が増えても、利用者の利益や働く人の状態が改善したとは限らないため、採用する指標とその限界を示します。

不利益には、プライバシーやセキュリティへの影響、障害、過重労働、依存先の固定、信用への影響、他の仕事を圧迫することなどを含められます。ある部門の工数削減が別の部門や顧客への作業移転による場合は、全体の削減と区別します。工数や費用の量と、人が感じる負担も分けます。

利益、利用機会、負担、リスクが、利用者、働く人、顧客、供給者などにどう分布するかを示します。分布の違いを確認したことと、それを公平と評価することは別です。誰の価値や優先順位で推奨したかを明らかにします。

## 実施能力と根拠

実行可能性は、予算、人員、技術上の依存、調達、変更への支援、必要な管理策がそろうかという判断です。雇用、消費者保護、プライバシー、セキュリティ、アクセシビリティ、契約、業種固有の制度は、案件の地域と時点に合わせて調べます。この参照モデルは適法性や承認を判定しません。

内部指標、実験、障害・事故の記録、利用者調査、財務モデル、外部比較を、答えたい問いに応じて使います。予測値と実績、利用した人の反応と利用できなかった人の経験、相関と因果の解釈を区別します。外部の成功事例は、条件が違う自社で同じ結果になる証拠として扱いません。

## 規定文書の改訂案を比較する

方針、業務手順、作業指示を改訂するときは、担当者がどの場面で何を判断・実行できるようにするかを要件とします。現行の権限や安全条件など、改訂後も維持すべき意味を確認します。同じ要件を満たす改訂案は、規定の内容と文書内の配置の組として扱います。

| 概念 | 確認すること |
| --- | --- |
| 判断場面 | 対象、担当、作業段階、判断を始める条件。 |
| 規定 | その場面で何を義務とし、許可し、禁止するか。誰に権限があり、どの優先関係や例外が適用されるか。 |
| 配置 | 判断時にどの節を読み、どこで関連する条件や例外を確かめるか。 |

複数の記述が同じ規定を表すかは、対象・担当・段階・発動条件に加え、行動とその義務・許可・禁止の別、権限、優先関係、例外を照合します。複数の段階で使う条件は、その意味を定める箇所と各段階の参照先を確認します。

各案に同じ問いと事例を当て、担当者がその時点で読む箇所からたどります。どの規定を根拠に何を行い、情報や権限が不足するときは何を保留するかを答えます。元の事例と、条件や権限の違いで答えが変わる境界例を使います。各案の要件充足と維持すべき規定への影響を確かめ、事例の情報不足と規定の曖昧さを区別します。

| 改訂の範囲 | 構成上の適合を確認する観点 |
| --- | --- |
| 既存節への追記 | その節がすでに同じ判断を扱い、追記が既存の規定の意味や手順の順序に沿う。 |
| 小節の追加と関連箇所の調整 | 既存の章に判断段階を置ける。関連する用語や権限の範囲を明確にするか、参照を設けると一貫して読める。 |
| 関係する章の再構成 | 複数の判断場面で規定が分散し、局所的な調整では根拠をたどりにくい。構成を改めると担当・手順・例外の関係を追いやすくなる。 |

要件を満たす案について、構成への適合、判断への効果、編集・レビュー・維持の負担をそれぞれ示します。構成への適合は節の役割、手順の順序、用語や規定の適用範囲で評価します。判断への効果は、担当者が必要な時点で規定を見つけ、根拠と次の行動を読み取れるかで評価します。構成への適合と判断への効果が同程度なら、負担の差も選択材料にします。文面を事例に当てて予測した効果と、実際の業務で観測した効果は区別します。

### 適用例

検証停止後の診断を作業指示に加える場合は、製品や納品先の要件、承認済みの資源制約、検証ツールの設定値を区別します。例えば、ツールの時間上限で止まった事例では、上限の根拠と最後に到達した段階を確認し、原因を絞る次の観測を選べるかを試します。メモリでは承認済みの予算内でツール設定を調整できる場面と、調整後の再実行が上限に抵触する場面を対にします。容量では納品ファイルの仕様上限、検証ログの出力上限、空きディスク下限で次の行動がどう変わるかを確かめます。再実行の条件がそろわないときは実行を保留し、可能な調査と受入検証を未完とする判断を区別できるかを確かめます。

起動前、実行中、停止後の順に読める章で、診断を扱う既存節がなければ、停止後の小節に診断を置く案が適合します。起動前の「資源上限」がツール設定値も含むように読める場合は、維持する範囲が承認済みの資源制約であることを関連箇所にも明記します。同様に、資料の回収手順を改める場合は、再生成可能な一時ファイルと唯一の受領原本を事例とし、それぞれ誰がどの条件を確かめれば回収できるかを比較します。

## 適用を確かめる

例えば業務ツールの価格だけが予算上限を超えた場合、資源と採用条件を見直します。価格の変更だけから、生産性の効果や利用者の価値まで低く評価しません。生産性向上が報告されていても、問い合わせ対応の増加が別部署に集中しているなら、その負担を併せて示します。

この資料は旧版の組織向け観点を再構成したローカルな参照モデルです。指標の増減や制度への適合を裏付ける一次資料としては使いません。価値の実現、利用、事故、費用、負担などの継続観察や停止条件は、依頼に含まれる場合に設計します。共通の報告と分野の組み合わせは [適用の指針](../adaptation-rules.md) に従います。
