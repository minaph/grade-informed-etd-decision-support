# 成果物・手順の利用説明モデル

## 目的と単位

成果物や手順を、ある目的と環境でどう使い、何を結果として期待できるか説明するモデルです。一件は、特定の成果物または手順についての、一つの利用場面に対応する説明です。文書、コード、コマンド、道具、操作手順などを扱えます。

## 構成要素と関係

| 概念 | 定義 |
| --- | --- |
| 成果物・手順 | 利用する対象の内容と、区別が必要な版・設定。 |
| 利用目的と環境 | 何のために使い、どの環境・対象に適用するか。 |
| 入力・操作・前提 | 必要な入力、行う操作、成立に必要な条件。 |
| 期待される結果 | 前提と操作が成立した場合に得られると考えられる出力・状態。 |
| 確認された結果 | 実際に確認した出力・状態と、その実行条件。未実行の場合は期待結果と分ける。 |
| 変形と失敗条件 | 用途に合わせて変えられる部分と、動作しない・意図を満たさない条件。 |

期待結果は、入力・操作・前提の組み合わせに対応します。異なる版や環境での確認結果を、条件を外して保証として扱いません。変形例は元の成果物との違いが分かるようにし、どの目的や条件に対応するかを示します。

## 記述方法

中心となる成果物や手順を示し、利用に必要な入力、操作、結果、失敗条件をつなげます。説明だけを求められた場合に実行済みと表現せず、確認した場合はその条件と範囲を伝えます。実行結果が不明であることと失敗したことは区別します。

使用例は理解に必要な場合に添え、例示、仕様からの推論、実測結果を読み分けられるようにします。コードや画像は記述の媒体であり、それ自体が動作確認の証拠になるわけではありません。コマンドのみなどの形式指定では、必要な内容を指定形式で返し、全項目の説明を追加しません。

このモデルは利用説明を定めます。実行の承認、実行代行、実装計画、保守や監視の手順は定めません。依頼された行為の結果を説明する場合も、何を実際に行ったかに合わせます。

## 適用例と境界

架空のツールで `items --format json` が一覧をJSONで返す仕様だとします。仕様に基づく説明なら、期待される結果はJSON形式の一覧ですが、実行を確認したことにはなりません。ある版で試して成功しても、別の版の動作は別途確認が必要です。

使い方が分かることと、そのツールを採用する価値があることは別の判断です。利用説明のために、代替製品との評価表を必ず作る必要はありません。

## 定義を確かめる問い

- 入力・操作・前提と期待結果の関係を表せるか。
- 仕様上の期待、実行で確認した結果、未確認、失敗を区別できるか。
- 版や環境の違い、変形例、失敗条件を必要な範囲で説明できるか。
