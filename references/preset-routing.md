# 概念モデルの選択とケースへの適用

この文書は、親ワークフローが管理する参照モデルから、現在の状況とタスクに合う構成を選び、モデルの不足とケース情報の不足を切り分けるために使う。個別プリセットの定義や改訂方針を、この文書で一律に定めるものではない。

汎用的なヒアリング、モデルの適用評価・定義・改訂の方法には、同梱した `skills/conceptual-modeling/SKILL.md` を使う。ここに記す `skills/` と `references/` のパスは親スキルのルートから解決する。子スキル内の参照は子のルートから解決する。依存先が未取得なら、READMEのsubmodule取得手順で復元する。別に導入された最新版で黙って代用しない。

## 1. 親と概念モデリングスキルの役割

親は、プリセット定義とCQの管理、ContextとQuestionsの形成、モデルの採用判断、成果のEtDへの反映を担当する。子は、渡された目的・資料・実例・定義に対して、要件整理、表現能力の評価、定義や改訂の作業を行う。子へ親のQuestions形式やEtD評価の規則を持ち込まない。

既存モデルの通常の適用で足りる場合は、そのモデルの定義に従って進める。適合性や意味の境界が不明、または定義変更が必要な場合に、子の方法を利用する。モデルを使うたびに全工程を繰り返す必要はない。

## 2. CQとQuestionsを対応づける

CQは、モデル定義に付随する表現要件である。モデルが何を区別し、どのような問いを扱えるべきかを示す。Questionsは、現在の状況とタスクに属し、どの違いが選択肢や行動を変えるかを `premise`・`splitter`・`actions` で表す。帰属先としてはケース側に近いが、CQの単純なインスタンスではない。具体性だけで両者を区別せず、帰属と役割で判断する。

プリセットを選ぶ際は、重要なQuestionが必要とする対象、関係、条件、区別を、そのモデルのCQを状況に具体化した問いとして表せるかを確認する。これを、この文書では「包含」と呼ぶ。自然言語の意味に基づく対応であり、文字列の類似、件数、形式的な集合包含で採否を決めない。

次の三点を分けて確認する。

| 確認 | 判断すること |
| --- | --- |
| 要求の対応 | Questionに必要な区別がCQの対象に含まれるか |
| 定義の裏付け | 概念・関係・プロパティがその区別を表現できるか |
| ケース情報の充足 | 今回、その値や根拠を得ているか |

前二つはモデル適合性、三つ目は主に情報状態の問題である。CQの宣言だけで能力が確認されたとはみなさない。対応するCQがない場合も定義を確認し、能力の説明不足と構造不足を分ける。必要なら、具体化した問いを既存例へ適用して確かめる。

一つのQuestionを複数CQが支える場合も、一つのCQから複数のケースの問いが生じる場合もある。モデルが扱うのはQuestionに必要な情報上の区別であり、それだけでユーザーの価値、許容閾値、行動の選択を確定しない。モデルをまたぐ必要がある場合は、欠ける区別と各モデルの責任範囲を示し、当該成果物の合成規則に従う。

例えば、モデルのCQが「移行方式ごとの復旧条件・所要時間・データ損失を比較できるか」であり、Questionが「停止可能時間30分の状況で、許容する損失内に復旧できるかによって移行方式を選ぶ」なら、時間・損失・条件をモデルが表現できるかを調べる。「可逆性：高・中・低」だけでは必要な詳細度に足りない可能性がある。表現できても実測値がなければ、モデル不足ではなく情報不足として扱う。30分という閾値の根拠はケース側で確認する。

## 3. 候補比較と問いの形成を往復する

### 3.1 状況と用途から候補を絞る

Context、暫定Questions、利用目的、既存資料を確認する。候補モデルの対象・状況・目的・除外条件を照合し、関係する候補を選ぶ。適用範囲と、判断に必要な詳細度の二軸で比較する。適切な候補がなければ、ケース固有の仮定義から始められる。

候補ごとに、何を一件と数え、どの単位で比較するかを確認する。候補の比較と対象の分割を往復し、重要な違いを保持できる構成を選ぶ。一般的な分類へ先に固定し、事例を押し込めない。

### 3.2 重要なQuestionsをCQと定義へ照合する

第2節の三点を使い、支持できる区別、部分的にしか扱えない区別、未確認の能力、対象外の区別を明らかにする。判断を変え得る不足を優先し、CQの包含率や網羅数を得点化しない。

### 3.3 候補から見落としを点検する

候補のCQや定義によって、最初のQuestionsになかった重要な論点が見つかる場合がある。その論点が選択肢や条件を変えるなら、ContextまたはQuestionsへ反映して候補を再評価する。全CQをQuestionsへ展開しない。プリセットはケースの事実・根拠・権威・ユーザーの価値判断の代用ではない。

QuestionsとContextの更新、その後のTreeと選択肢の再生成は `references/question-formation.md` に従う。CQのIDや対応表をFormationの必須プロパティとして追加しない。重要な対応と不足を短い説明で残せばよい。

## 4. 差分の影響から対応を選ぶ

不足や候補間の違いについて、次の何が変わるかを確認する。

- 成立する選択肢と、その実現可能性。
- 必要な根拠、その解釈、追加確認。
- 価値、リスク、受容性、資源、実施条件。
- 結論、結論に付す条件、再評価の必要性。

| 状況 | 対応 |
| --- | --- |
| 適用範囲・詳細度が合い、重要な区別を保持できる | 現行モデルを採用する |
| 表現できるが、今回の値や根拠がない | インスタンスに未確認等を残し、重要なら確認方法を選ぶ |
| 既存の意味を保った補足で足りる | 理由と影響を示して局所補足し、再評価する |
| 構造や相互作用の不足が判断を変え得る | 子の方法でケース固有の定義・拡張・再設計を検討する |
| 一部の問いだけ適合する | 部分適用の範囲と、残りを扱う方法を明示する |
| 対象や意味が合わず、無理な読み替えが必要 | 不採用にし、別候補またはケース固有モデルを検討する |

「暫定属性」という名称でも、対象単位や既存の意味を変えるなら定義変更として扱う。値の補充と構造の追加を混同しない。複数の定義を組み合わせる場合も、意味と情報状態を引き継ぎ、その成果物に適用される組み合わせの制約を守る。

重要な情報不足には、何を、どの方法で確認し、その方法が適する理由と、値が変わったときの判断影響を残す。ResearchとInterviewの選択は情報の性質で判断し、質問の実施時期は親のFormationの規則に従う。

## 5. ケースへ反映し、完了または改訂へ進む

採用した定義と、その定義に照らしたケースの値を分ける。複数の表現をまとめる場合も、どの意味を採用したか、重要な出所、値の確定性を保持する。固定の統合インスタンス形式は要求しない。

子から得た定義、適用評価、残件を親が解釈し、情報・制約・不確実性はContextへ、重要な分岐はQuestionsへ反映する。変化が重要ならTreeと選択肢を再生成し、EtD評価への影響を確認する。モデルが回答を表現できることと、ケースの回答や推奨が根拠によって支持されることは分ける。

参照モデルまたは依頼元が今回の作業の完了条件を定めている場合は、その条件を適用する。以下の安定性に基づく完了判断は、固有の完了条件がない場合の暫定基準とする。

今回の判断に必要な区別を扱え、残る不確実性と影響を説明でき、追加のモデル変更が結論や条件を変えそうにない場合は、採用理由と再検討条件を示して暫定的に完了する。目的を満たせない場合は、能力不足・情報不足・要件未決のどこが残るかを示し、充足したと報告しない。

共有モデルへの反映では、観察、改訂候補、具体的な改訂案、正式反映を分ける。再利用を提案する場合は成立条件・再発性・抽象化可能性を調べる。一度の反例でも中心定義の誤りを示す場合は改訂を検討でき、再発回数を修正の必須条件にしない。親が管理するモデルへの正式反映は、その管理・承認・版の規則に従う。
