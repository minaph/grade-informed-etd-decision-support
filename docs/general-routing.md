# 指示の詳しさによらない一般ルーティング

状態：採用。決定日：2026年9月15日。

## Narrative Upscaling の吸収

Narrative Upscaling が固有に扱う条件を、直接のタスク指示だけでは何にどう回答すべきか不十分・曖昧な場合と定めます。短文であること自体は条件ではありません。詳細な入力でも目的が不明なことがあり、短い入力でも回答対象や形式が確定していることがあります。

現行の内容を点検すると、モデル選択、調査・聞き取り、併用、回答、拡充の終了は一般対応と共通でした。モデル定義は既に独立ファイルへ分離され、指示不足時だけのモデル集合も必要ありません。固有の処理は、未確定の目標・価値・選択肢を仮説として補い、別解釈を保って探索する短い入口の分岐にまとめられます。

短い独立ガイドを残す案も検討しましたが、一般手順との読み分けと重複管理が残り、参照順序が曖昧になるため採用しません。SKILL.md に吸収し、旧ファイルへの参照は現行の手順へ切り替えます。過去の名称は評価ケースの識別子や履歴には残せます。

## 共通のモデル集合と入口

指示が十分な場合と不十分な場合で、利用できるモデルを分けません。指示の充足度は解釈の暫定性と確認の必要性に影響します。具体的な目的が異なれば採用するモデルは変わり得ますが、入力の詳しさだけで候補集合を制限しません。

状況の description、親が供給する sensemaking、objects を整理し、毎回の最小の内部構造確認を行います。その後、目的に合うモデルを暫定選択し、情報収集と解釈の更新を往復します。必要な区別が明らかな場合に、詳しいモデル適合性検討を毎回強制しません。既存の意思決定構造化の形式と表示条件は維持します。

## 選択用メタデータ

各モデル資料の冒頭に、name、description、kind を置きます。name は一覧内で資料を識別する名前、description は内容と用途、kind は文書の役割です。モデルの意味や適用範囲を変更する定義ではなく、本文を読む候補を選ぶ手掛かりです。

report-model、domain-model に加え、methodology、redirect、registry を区別します。これにより方法論資料や参照窓口を、独立した報告モデルと混同しにくくします。役割をまたぐ併用を禁止する分類にはしません。タグや前提関係の網羅的なメタデータは設けず、必要な違いは説明に含めます。

Markdown は frontmatter、既存の公式プロファイル YAML はルートの項目として追加します。公式プロファイル本体、出典、確認日は変更しません。一覧スクリプトはファイルから都度取得し、別の手動インデックスは作りません。スクリプトを実行できなくても、検索や冒頭の参照で候補を選べます。

## 確認と再検討

設計レビューでは、入力の長さと不足の区別、十分な指示でも必要な仮説を検討できること、一覧スクリプトを必須にしないこと、kind を排他的フィルタにしないこと、旧参照の更新を確認しました。

メタデータの検査と、指示の詳しさを変えた評価ケースで動線を確認します。実際のモデル選択精度や読込コストの改善は未実証です。説明だけでは候補を区別しにくい例が見つかった場合は、分類項目を増やす前に description と本文の境界を見直します。
